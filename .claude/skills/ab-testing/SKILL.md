# A/B 테스트 & 실험 (A/B Testing)

A/B 테스트/실험을 설계하거나, 지속적인 성장 실험 프로그램을 구축할 때 적용합니다. (트래킹 구현
자체는 이 범위 밖, 페이지 레벨 CRO 아이디어 생성은 `cro` 스킬 참고)

## 설계 전 파악할 것

1. **테스트 맥락**: 무엇을 개선하려 하는가? 어떤 변경을 고려 중인가?
2. **현재 상태**: 베이스라인 전환율은? 현재 트래픽 볼륨은?
3. **제약**: 기술적 복잡도, 일정, 사용 가능한 도구

## 핵심 원칙

1. **가설로 시작**: "어떻게 되나 보자"가 아니라 근거/데이터 기반의 구체적 예측
2. **하나만 테스트**: 테스트당 단일 변수 — 아니면 무엇이 효과를 냈는지 알 수 없음
3. **통계적 엄격함**: 표본 크기를 사전에 정하고, 중간에 훔쳐보고 멈추지 말 것, 방법론을 끝까지 지킬 것
4. **중요한 것을 측정**: 비즈니스 가치와 연결된 주 지표, 맥락을 위한 보조 지표, 해를 막기 위한
   가드레일 지표

## 가설 프레임워크

구조: "[관찰/데이터]이기 때문에, 우리는 [변경]이 [오디언스]에게 [기대 결과]를 가져올 것이라 믿는다.
이는 [지표]로 확인할 것이다."

- **약함**: "버튼 색을 바꾸면 클릭이 늘지도 몰라요."
- **강함**: "히트맵과 피드백에 따르면 사용자가 CTA를 찾기 어려워하므로, 버튼을 키우고 대비되는
  색을 쓰면 신규 방문자의 CTA 클릭률이 15% 이상 늘 것이라 믿는다. 페이지뷰→가입시작 클릭률로
  측정한다."

## 테스트 유형

| 유형 | 설명 | 필요 트래픽 |
|---|---|---|
| A/B | 두 버전, 단일 변경 | 보통 |
| A/B/n | 다중 변형 | 더 높음 |
| MVT(다변량) | 여러 변경의 조합 | 매우 높음 |
| Split URL | 변형마다 다른 URL | 보통 |

## 표본 크기 빠른 참조

| 베이스라인 | 10% 상승 | 20% 상승 | 50% 상승 |
|---|---|---|---|
| 1% | 변형당 15만 | 변형당 3.9만 | 변형당 6천 |
| 3% | 변형당 4.7만 | 변형당 1.2만 | 변형당 2천 |
| 5% | 변형당 2.7만 | 변형당 7천 | 변형당 1,200 |
| 10% | 변형당 1.2만 | 변형당 3천 | 변형당 550 |

정확한 계산은 Evan Miller's 또는 Optimizely's 표본 크기 계산기 사용을 권장.

## 지표 선정

- **주 지표**: 가장 중요한 단일 지표, 가설과 직결, 테스트 판정에 사용
- **보조 지표**: 주 지표 해석을 뒷받침(왜/어떻게 작동했는지 설명)
- **가드레일 지표**: 악화되면 안 되는 것들. 유의미하게 나빠지면 테스트 중단
- 예(가격 페이지 테스트): 주=플랜 선택률, 보조=페이지 체류시간·플랜 분포, 가드레일=지원 티켓·환불율

## 변형 설계

**바꿀 수 있는 것**: 헤드라인/카피(메시지 앵글, 가치제안, 구체성, 톤), 비주얼 디자인(레이아웃,
색, 이미지, 위계), CTA(버튼 카피, 크기, 배치, 개수), 콘텐츠(포함 정보, 순서, 양, 소셜프루프)

**베스트 프랙티스**: 단일하고 의미 있는 변경, 차이를 만들 만큼 과감하게, 가설에 충실하게

## 트래픽 배분

| 방식 | 분할 | 사용 시점 |
|---|---|---|
| 표준 | 50/50 | 일반적인 A/B 기본값 |
| 보수적 | 90/10, 80/20 | 나쁜 변형의 리스크 제한 |
| 램핑 | 소규모로 시작해 점차 증가 | 기술적 리스크 완화 |

고려사항: 재방문 시 같은 변형을 보도록 일관성 유지, 시간대/요일에 걸쳐 균형 있게 노출

## 실행

**진행 전 체크리스트**: 가설 문서화 / 주 지표 정의 / 표본 크기 계산 / 변형 정확히 구현 / 트래킹
검증 / 모든 변형 QA 완료

**진행 중**: 기술적 이슈 모니터링, 세그먼트 품질 체크, 외부 요인 기록 / 하지 말 것 — 중간에 결과
훔쳐보고 조기 중단, 변형을 중간에 수정, 새 트래픽 소스 추가

**훔쳐보기 문제**: 표본 크기 도달 전 결과를 보고 조기 중단하면 거짓 양성과 잘못된 의사결정으로
이어짐. 표본 크기를 사전에 확정하고 그 과정을 신뢰할 것.

## 결과 분석

- **통계적 유의성**: 95% 신뢰 = p < 0.05, 즉 결과가 우연일 확률이 5% 미만이라는 뜻(보장은 아님)
- **체크리스트**: 표본 크기 도달? 통계적으로 유의? 효과 크기가 의미 있는가(MDE 대비)? 보조 지표가
  일관되는가? 가드레일에 문제는 없는가? 세그먼트별 차이(모바일 vs 데스크톱, 신규 vs 기존)는?
- **결과 해석**: 유의한 승리 → 변형 적용 / 유의한 패배 → 컨트롤 유지, 이유 학습 / 유의차 없음 →
  트래픽 더 필요하거나 더 과감한 테스트 필요 / 신호 혼재 → 더 깊이 파거나 세그먼트 분석

## 성장 실험 프로그램

개별 테스트도 가치 있지만, 지속적인 실험 프로그램은 복리로 쌓이는 자산입니다.

**실험 루프**: 가설 생성(데이터/리서치/경쟁사/고객 피드백에서) → ICE 스코어링으로 우선순위 →
설계·실행 → 통계적으로 엄격하게 분석 → 승자를 플레이북에 승격 → 학습에서 새 가설 생성 → 반복

**가설 소스**: 애널리틱스(이탈 지점, 저전환 페이지), 고객 리서치(고통점, 혼란), 경쟁사 분석(그들의
기능/메시징/UX), 지원 티켓(반복 질문/불만), 히트맵/녹화(주저·분노클릭·이탈 지점), 과거 실험
("유의한 패배" 테스트가 새 각도를 보여주기도 함)

**ICE 우선순위화**: Impact(먹히면 주 지표를 얼마나 움직이는가), Confidence(데이터 기반으로 얼마나
확신하는가), Ease(얼마나 빠르고 싸게 만들고 측정할 수 있는가) 각 1-10점, ICE = (I+C+E)/3.
높은 점수부터 실행, 매달 재점수화.

**실험 속도 지표**: 월 실험 수 4-8건(대부분 팀 기준), 승률 20-30%(성숙한 프로그램의 일반적 수치 —
지속적으로 더 높다면 가설이 너무 보수적일 수 있음), 평균 테스트 기간 2-4주, 백로그 20개 이상 유지

**실험 플레이북**: 테스트가 이기면 적용만 하지 말고 패턴을 문서화 — 실험명/날짜/가설/표본크기/
결과(승패+수치+신뢰구간+p값)/가드레일 결과/세그먼트별 차이/왜 작동했는지/재사용 가능한 패턴/
적용 가능한 다른 페이지/상태(적용됨·보류·후속테스트 필요)

**케이던스**: 주간(30분) 진행 중 실험의 기술 이슈·가드레일 점검 / 격주 완료 실험 결론·플레이북
업데이트·다음 실험 시작 / 월간(1시간) 실험 속도·승률·누적 효과 리뷰, 백로그 보충, ICE 재우선순위화 /
분기 플레이북 감사

## 흔한 실수

- **설계**: 너무 작은 변경(감지 불가), 너무 많은 변경(원인 특정 불가), 명확한 가설 부재
- **실행**: 조기 중단, 테스트 중 변경, 구현 검증 누락
- **분석**: 신뢰구간 무시, 세그먼트 체리피킹, 무의미한 결과 과잉 해석
